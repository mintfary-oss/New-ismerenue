## 1. ОБЩАЯ МОДЕЛЬ БЕЗОПАСНОСТИ

### 1.1 Принципы защиты

Система построена на трёх уровнях защиты — каждый независим и компенсирует возможные слабости другого:

```
Интернет
    │
    ▼
┌─────────────────────────────────────────────┐
│  Уровень 1: СЕТЬ (Nginx + TLS)              │
│  • TLS 1.3, HSTS, rate limiting по IP       │
│  • Блокировка прямых IP-запросов            │
│  • Nginx proxy — единственный вход          │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│  Уровень 2: ПРИЛОЖЕНИЕ (Go + Chi)           │
│  • JWT аутентификация + blacklist           │
│  • RBAC авторизация                         │
│  • Rate limiting по IP/пользователю         │
│  • Security headers, CSP                    │
│  • Prepared statements (SQL-injection)      │
└──────────────────┬──────────────────────────┘
                   │
                   ▼
┌─────────────────────────────────────────────┐
│  Уровень 3: ДАННЫЕ (PostgreSQL + Redis)     │
│  • Argon2id хеши паролей                    │
│  • HMAC-SHA256 хеши API-токенов             │
│  • JWT blacklist в Redis                    │
│  • Изолированная сеть — порты не открыты   │
└─────────────────────────────────────────────┘
```

### 1.2 Threat Model — от чего защищаемся

| Угроза | Механизм защиты | Уровень |
|--------|----------------|---------|
| Перехват трафика | TLS 1.3 + HSTS | Сеть |
| Брутфорс паролей | Argon2id + блокировка после 5 попыток | Приложение |
| Похищение токена | JWT blacklist + 15 мин TTL | Приложение |
| SQL-инъекция | pgx prepared statements | Данные |
| XSS | CSP + X-XSS-Protection | Приложение |
| CSRF | SameSite cookies + CORS | Приложение |
| DDoS | Rate limiting (Nginx + Go) + limit_conn | Сеть |
| Privilege escalation | RBAC + no-new-privileges | Контейнер |
| Утечка данных | Изолированная Docker-сеть | Инфраструктура |
| Сканирование | return 444 для неизвестных Host | Сеть |
| Timing-атаки | constant-time compare + dummy hash | Приложение |

## 2. АУТЕНТИФИКАЦИЯ

### 2.1 Схема JWT — двойной токен

Используется схема с двумя токенами для баланса безопасности и удобства:

```
[Клиент]  ──POST /auth/login──>  [Сервер]
              email + password
                                   проверка Argon2id
                                   ↓
[Клиент]  <──────────────────────  [Сервер]
          access_token  (15 мин)
          refresh_token (30 дней)
               │
               │  каждый запрос
               ▼
[Клиент]  ──Authorization: Bearer <access_token>──>  [Сервер]
                                                        JWT verify
                                                        blacklist check
                                                        ↓
[Клиент]  <─────────────────────────────────────  [Сервер]
                        данные / 401
```

### 2.2 Параметры JWT

| Параметр | Значение | Обоснование |
|---------|---------|-------------|
| Алгоритм | HMAC-SHA256 | Быстро, надёжно, без асимметрии |
| Access TTL | **15 минут** | Минимизирует окно при похищении |
| Refresh TTL | **30 дней** | Удобство + безопасность |
| Секрет | 64 случайных символа | Брутфорс нереален |
| Поле `jti` | UUID v4 (уникальный ID) | Нужен для blacklist |
| Поле `uid` | User ID | Идентификатор пользователя |
| Поле `role` | admin/analyst/user | Роль для RBAC |

### 2.3 JWT Blacklist (мгновенный отзыв)

Стандартный недостаток JWT — нельзя отозвать до истечения TTL. Мы решаем это через Redis:

```go
// При logout — добавляем JTI в blacklist:
func (b *TokenBlacklist) Add(ctx, tokenID string, expiry time.Time) error {
    ttl := time.Until(expiry)  // храним только до истечения токена
    return b.client.Set(ctx, "blacklist:token:"+tokenID, "1", ttl).Err()
}

// При каждом запросе — проверяем blacklist:
blacklisted, _ := validator.IsBlacklisted(ctx, claims.TokenID)
if blacklisted {
    writeError(w, 401, "токен отозван")
    return
}
```

**Что это даёт:** при logout токен немедленно становится недействительным, даже если его TTL ещё не истёк. Украденный токен при logout жертвы также перестаёт работать.

### 2.4 Refresh-механизм

```
Клиент                          Сервер
  │                               │
  │  access_token истёк           │
  │──POST /auth/refresh ────────> │
  │   {refresh_token: "..."}      │
  │                               │  проверка refresh_token
  │                               │  добавление старого в blacklist
  │                               │  генерация новой пары токенов
  │ <─── {access_token, refresh}──│
  │                               │
```

Ротация при refresh: старый refresh_token добавляется в blacklist, выдаётся новая пара. Это предотвращает повторное использование украденного refresh_token.

### 3.3 Реализация RBAC в коде

```go
// internal/middleware/rbac.go

// Проверка роли — O(1) через map
func RequireRole(roles ...domain.Role) func(http.Handler) http.Handler {
    allowed := make(map[domain.Role]struct{}, len(roles))
    for _, r := range roles { allowed[r] = struct{}{} }

    return func(next http.Handler) http.Handler {
        return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
            claims := ClaimsFromContext(r.Context())
            if claims == nil {
                writeError(w, 401, "требуется авторизация")
                return
            }
            if _, ok := allowed[domain.Role(claims.Role)]; !ok {
                writeError(w, 403, "недостаточно прав доступа")
                return
            }
            next.ServeHTTP(w, r)
        })
    }
}
```

Middleware применяется **на каждом защищённом маршруте** — нет возможности "обойти" через другой путь.

## 4. ЗАЩИТА ПАРОЛЕЙ

### 4.1 Argon2id — почему это лучший выбор

| Алгоритм | Устойчивость к GPU | Время хеша | Рекомендован |
|---------|:------------------:|:----------:|:------------:|
| MD5 | ❌ взламывается мгновенно | < 1 мс | ❌ |
| SHA256 | ❌ GPU ускоряет в 1000× | < 1 мс | ❌ |
| bcrypt | ⚠️ частично | ~100 мс | устаревший |
| scrypt | ✅ | ~150 мс | хорош |
| **Argon2id** | ✅✅ | ~200 мс | **OWASP 2025** |

Argon2id выиграл международный конкурс Password Hashing Competition (2015). Рекомендован OWASP в 2025 году как **первый выбор** для хеширования паролей.

### 4.2 Параметры Argon2id в нашей реализации

```go
// internal/config/loader.go
v.SetDefault("auth.argon2_time",    3)      // 3 итерации
v.SetDefault("auth.argon2_memory",  65536)  // 64 MB памяти на хеш
v.SetDefault("auth.argon2_threads", 4)      // 4 параллельных потока
v.SetDefault("auth.argon2_key_len", 32)     // 256-бит ключ
```

Что это означает для злоумышленника:
- На GPU RTX 4090: **~8 попыток/секунду** (vs 10 миллиардов для MD5)
- Перебор словаря из 10 млн слов займёт **14 дней** на лучшем оборудовании
- Перебор всех 8-значных паролей (a-z,0-9): **нереален**

### 4.3 Формат хранения

```
$argon2id$v=19$m=65536,t=3,p=4$<salt_base64>$<hash_base64>
```

- Соль генерируется случайно (`crypto/rand`) для каждого пароля
- Одинаковые пароли дают **разные хеши** — радужные таблицы бесполезны
- Параметры хранятся внутри строки — можно менять при обновлении

### 4.4 Защита от timing-атаки

При неверном логине сервер всегда выполняет хеширование "вхолостую":

```go
// Если пользователь не найден — тратим то же время на dummy-хеш
// Злоумышленник не может определить "пользователь существует" по времени ответа
_ = s.verifyPassword("dummy_password_for_timing_protection",
    "$argon2id$v=19$m=65536,t=3,p=4$AAAA...$AAAA...")
```

Финальная проверка использует `crypto/subtle.ConstantTimeCompare` — время не зависит от совпадения байтов.

## 5. API-ТОКЕНЫ

### 5.1 Назначение

API-токены используются для аутентификации датчиков и внешних систем без привязки к паролю пользователя.

### 5.2 Схема безопасности

```
Создание токена:
1. crypto/rand генерирует 32 случайных байта → raw_token (hex, 64 символа)
2. HMAC-SHA256(raw_token, JWT_SECRET) → token_hash
3. В БД хранится: user_id, name, token_hash, is_active, expires_at
4. Пользователю возвращается raw_token — ОДИН РАЗ

Проверка токена:
1. Получаем Bearer <raw_token> из заголовка
2. Вычисляем HMAC-SHA256(raw_token, JWT_SECRET)
3. Ищем token_hash в БД (O(1) по уникальному индексу)
4. Проверяем is_active и expires_at
```

**Ключевые свойства:**
- В базе данных **никогда не хранится** сам токен — только его HMAC
- Компрометация БД не даёт злоумышленнику реальные токены
- Каждый датчик получает **отдельный** токен — компрометация одного не влияет на остальных
- Токен можно мгновенно отозвать через Admin Panel

## 6. ЗАЩИТА ОТ БРУТФОРСА

### 6.1 Блокировка аккаунта

```
Попытки входа для одного email:

Попытка 1 → неверный пароль → счётчик Redis: 1
Попытка 2 → неверный пароль → счётчик Redis: 2
Попытка 3 → неверный пароль → счётчик Redis: 3
Попытка 4 → неверный пароль → счётчик Redis: 4
Попытка 5 → неверный пароль → счётчик Redis: 5
Попытка 6 → HTTP 429 "аккаунт временно заблокирован" (15 минут)
...
После 15 минут → счётчик сбрасывается → снова можно попробовать
При успешном входе → счётчик сбрасывается немедленно
```

Реализация через Redis с TTL:

```go
// При первой попытке устанавливаем TTL = lockout_duration
if count == 1 {
    client.Expire(ctx, "login_attempts:"+email, lockoutDuration)
}
```

Преимущество Redis: при перезапуске приложения счётчики **сохраняются** — злоумышленник не может перезагрузить сервис чтобы сбросить счётчик.

### 6.2 Rate Limiting на уровне приложения (Go)

```go
// internal/middleware/ratelimit.go — token bucket по IP

var (
    LoginLimiter  = NewRateLimiter(10,  15*time.Minute, 30*time.Minute)
    APILimiter    = NewRateLimiter(100,  1*time.Minute,  5*time.Minute)
    WidgetLimiter = NewRateLimiter(300,  1*time.Minute,  5*time.Minute)
)
```

При превышении лимита возвращается HTTP 429 с заголовком `Retry-After: 60`.

### 6.3 Rate Limiting на уровне Nginx (второй рубеж)

```nginx
# docker/nginx/nginx.conf

limit_req_zone $binary_remote_addr zone=auth_limit:10m   rate=10r/m;
limit_req_zone $binary_remote_addr zone=api_limit:10m    rate=60r/m;
limit_req_zone $binary_remote_addr zone=widget_limit:10m rate=120r/m;

# Максимум 20 одновременных соединений с одного IP
limit_conn_zone $binary_remote_addr zone=conn_limit:10m;
limit_conn conn_limit 20;
```

**Двухуровневая защита:** даже если злоумышленник обходит Nginx — Go-middleware блокирует запросы. Даже если обходит Go — Nginx блокирует на уровне TCP.

Nginx ограничивает соединения до того, как они достигают Go-приложения. Запрос, превысивший `limit_conn`, закрывается на уровне Nginx — Go-приложение не тратит ресурсы.

## 8. HTTP-ЗАГОЛОВКИ БЕЗОПАСНОСТИ

### 8.1 Заголовки API-маршрутов

```http
HTTP/1.1 200 OK
X-Content-Type-Options: nosniff
X-XSS-Protection: 1; mode=block
Referrer-Policy: strict-origin-when-cross-origin
X-Frame-Options: SAMEORIGIN
Permissions-Policy: geolocation=(), microphone=(), camera=()
Content-Security-Policy: default-src 'none'
Server: aqi-platform
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload  (при HTTPS)
```

### 8.2 Что каждый заголовок защищает

| Заголовок | От чего защищает | Пример атаки |
|-----------|-----------------|-------------|
| `X-Content-Type-Options: nosniff` | MIME sniffing | Загрузка JS под видом изображения |
| `X-XSS-Protection: 1; mode=block` | Отражённый XSS | `<script>alert(1)</script>` в параметре |
| `X-Frame-Options: SAMEORIGIN` | Clickjacking | Встраивание платформы во враждебный iframe |
| `Referrer-Policy` | Утечка URL | Заголовок Referer со sensitive данными |
| `Permissions-Policy` | Снятие отпечатков | Тихий доступ к геолокации |
| `Content-Security-Policy: default-src 'none'` | XSS для API | Браузер не выполняет скрипты в JSON |
| `HSTS` | Downgrade-атака | Принудительное перенаправление на HTTP |
| `Server: aqi-platform` | Fingerprinting | Скрывает версию Go и ОС |

### 8.3 Заголовки для публичного виджета (iframe)

```http
Content-Security-Policy: default-src 'self';
  script-src 'self' 'unsafe-inline';
  style-src 'self' 'unsafe-inline';
  img-src 'self' data: https://*.tile.openstreetmap.org;
  connect-src 'self' https://*.openstreetmap.org;
  frame-ancestors *
```

Виджет намеренно разрешает `frame-ancestors *` (встраивание на любом сайте) — это требование ТЗ. При этом ограничивается набор разрешённых источников для всего остального.

### 8.4 CORS-политика

```go
cors.Handler(cors.Options{
    AllowedOrigins:   []string{"*"},
    AllowedMethods:   []string{"GET", "POST", "PUT", "PATCH", "DELETE", "OPTIONS"},
    AllowedHeaders:   []string{"Accept", "Authorization", "Content-Type", "X-Request-Id"},
    ExposedHeaders:   []string{"X-Request-Id"},
    AllowCredentials: true,
    MaxAge:           300,
})
```

`AllowedOrigins: *` при `AllowCredentials: true` — работает корректно: браузеры разрешают это сочетание, а CORS не защищает от серверных запросов (только браузерных).

## 9. TLS / HTTPS

### 9.1 Конфигурация TLS в Nginx

```nginx
ssl_protocols TLSv1.2 TLSv1.3;
ssl_ciphers ECDHE-ECDSA-AES128-GCM-SHA256
           :ECDHE-RSA-AES128-GCM-SHA256
           :ECDHE-ECDSA-AES256-GCM-SHA384
           :ECDHE-RSA-AES256-GCM-SHA384
           :ECDHE-ECDSA-CHACHA20-POLY1305
           :ECDHE-RSA-CHACHA20-POLY1305;
ssl_prefer_server_ciphers off;
ssl_session_cache    shared:SSL:10m;
ssl_session_timeout  1d;
ssl_session_tickets  off;
ssl_stapling         on;
ssl_stapling_verify  on;
```

### 9.2 Что это означает

| Настройка | Что обеспечивает |
|-----------|----------------|
| `TLSv1.2 + TLSv1.3` | TLS 1.0 и 1.1 отключены (уязвимы к BEAST, POODLE) |
| `ECDHE-*` шифры | **Forward Secrecy** — даже при компрометации ключа прошлый трафик недоступен |
| `CHACHA20-POLY1305` | Быстро на мобильных устройствах без AES-NI |
| `ssl_prefer_server_ciphers off` | Браузер выбирает лучший шифр для себя |
| `ssl_session_tickets off` | Исключение атаки на возобновление сессии |
| `OCSP stapling` | Проверка отзыва сертификата без запроса к CA |

### 9.3 HSTS Preload

```http
Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
```

Браузер **запоминает на 1 год**: использовать только HTTPS. Директива `preload` позволяет внести домен в список браузеров — защита работает даже при первом посещении.

### 9.4 HTTP → HTTPS редирект

```nginx
server {
    listen 80;
    location /.well-known/acme-challenge/ { root /var/www/certbot; }
    location / { return 301 https://$host$request_uri; }
}
```

Все HTTP запросы автоматически перенаправляются на HTTPS с кодом 301.

### 9.5 Защита от сканеров (прямые IP-запросы)

```nginx
# Запрос без заголовка Host (прямо на IP) — закрываем без ответа
server {
    listen 443 ssl default_server;
    ssl_certificate     /etc/nginx/ssl/cert.pem;
    ssl_certificate_key /etc/nginx/ssl/key.pem;
    return 444;  # Nginx закрывает соединение без HTTP-ответа
}
```

Сканеры и боты, обращающиеся напрямую по IP-адресу без Host-заголовка, получают закрытое соединение — им не видно даже что здесь что-то работает.

## 10. ЗАЩИТА БАЗЫ ДАННЫХ

### 10.1 Prepared Statements — защита от SQL-инъекции

Все запросы к PostgreSQL используют pgx/v5 с параметризованными запросами:

```go
// internal/repository/user.go — НЕТ конкатенации строк
const q = `
    SELECT id, email, password, full_name, role, is_active, created_at
    FROM users WHERE email = $1`

err := r.db.QueryRow(ctx, q, email).Scan(...)  // $1 — безопасный параметр
```

Злоумышленник не может передать `' OR 1=1 --` — pgx экранирует значение как данные, а не интерпретирует как SQL.

### 10.2 Хранение паролей в БД

```sql
-- migrations/000001_init_schema.up.sql
CREATE TABLE users (
    id         UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email      TEXT UNIQUE NOT NULL,
    password   TEXT NOT NULL,  -- Argon2id хеш, НИКОГДА не plaintext
    ...
);
```

В поле `password` хранится только строка вида:
```
$argon2id$v=19$m=65536,t=3,p=4$<random_salt>$<hash>
```

### 10.3 Хранение API-токенов

```sql
CREATE TABLE api_tokens (
    id         UUID PRIMARY KEY,
    user_id    UUID NOT NULL REFERENCES users(id),
    name       TEXT NOT NULL,
    token_hash TEXT NOT NULL,  -- HMAC-SHA256, НЕ сам токен
    is_active  BOOLEAN DEFAULT true,
    expires_at TIMESTAMPTZ,
    ...
);
```

Если злоумышленник получит дамп БД — у него будет только HMAC хеш токена. Без знания `JWT_SECRET` восстановить исходный токен невозможно.

### 10.4 Сетевой доступ к PostgreSQL

PostgreSQL **не имеет** открытых портов наружу:

```yaml
# docker-compose.yml — нет блока ports: у postgres
postgres:
    image: timescale/timescaledb:latest-pg17
    networks:
      - aqi_internal
    # ports: не указан — доступен только внутри aqi_internal
```

Подключиться к базе данных снаружи контейнерной сети невозможно.

### 10.5 Пользователь БД с минимальными правами

```sql
-- Приложение работает от пользователя 'aqi', а не superuser 'postgres'
-- Пользователь 'aqi' имеет права только на таблицы своей базы
```

## 12. ЗАЩИТА КОНТЕЙНЕРОВ

### 12.1 `no-new-privileges`

```yaml
security_opt:
  - no-new-privileges:true
```

Запрещает процессу внутри контейнера получить повышенные привилегии через `setuid`/`setgid` бинарники. Даже если злоумышленник выполнит код внутри контейнера — он не сможет стать root.

### 12.2 `cap_drop: ALL`

```yaml
cap_drop:
  - ALL       # убираем все Linux capabilities
cap_add:
  - NET_BIND_SERVICE  # только необходимые
```

По умолчанию Docker даёт контейнерам 14 capabilities (в т.ч. `NET_ADMIN`, `SYS_PTRACE`). Мы убираем все и добавляем только необходимые.

| Сервис | cap_drop | cap_add |
|--------|----------|---------|
| `app` | ALL | NET_BIND_SERVICE |
| `redis` | ALL | — |
| `prometheus` | ALL | — |
| `nginx` | ALL | NET_BIND_SERVICE, CHOWN, SETUID, SETGID, DAC_OVERRIDE |
| `postgres` | — | (оставлены стандартные — TimescaleDB требует) |

### 12.3 Образ без shell (distroless)

Go-приложение использует `gcr.io/distroless/static-debian12:nonroot`:

```dockerfile
FROM gcr.io/distroless/static-debian12:nonroot
```

- Нет `/bin/sh`, `/bin/bash` — нельзя запустить shell даже при RCE
- Нет пакетного менеджера — нельзя установить инструменты
- Нет системных утилит (curl, wget, nc) — нельзя скачать вредоносный код
- Запуск от пользователя `nonroot` (UID=65532) — не root

### 12.4 Ограничения ресурсов

```yaml
deploy:
  resources:
    limits:
      memory: 256M    # Go-приложение
      cpus: "1.0"
    reservations:
      memory: 64M
```

Защита от атак типа "resource exhaustion" — один контейнер не может исчерпать всю RAM сервера.

### 12.5 Ограничение лог-файлов

```yaml
logging:
  driver: json-file
  options:
    max-size: "50m"
    max-file: "5"
    compress: "true"
```

Предотвращает атаку "log flooding" — заполнение диска через генерацию огромного количества запросов.

## 14. ЛОГИРОВАНИЕ И АУДИТ

### 14.1 Что логируется

Все HTTP-запросы логируются Nginx в JSON:

```json
{
  "time": "2026-08-12T10:00:00+03:00",
  "remote_addr": "1.2.3.4",
  "method": "POST",
  "uri": "/api/v1/auth/login",
  "status": 401,
  "body_bytes": 45,
  "request_time": 0.203,
  "upstream_time": "0.201",
  "ua": "Mozilla/5.0 ...",
  "x_request_id": "abc123"
}
```

Приложение логирует события безопасности через `slog`:

```
{"level":"WARN","ts":"2026-08-12T10:00:00Z","msg":"неудачная попытка входа",
 "email":"user@example.ru","attempts":3,"ip":"1.2.3.4"}

{"level":"ERROR","ts":"2026-08-12T10:01:00Z","msg":"аккаунт заблокирован",
 "email":"user@example.ru","lockout_minutes":15}
```

### 14.2 Prometheus метрики безопасности

| Метрика | Что показывает |
|---------|----------------|
| `aqi_http_requests_total{status="401"}` | Число неавторизованных запросов |
| `aqi_http_requests_total{status="429"}` | Число превышений rate limit |
| `aqi_http_requests_total{status="403"}` | Число запрещённых действий |
| `aqi_http_request_duration_seconds` | Аномальное время (возможная атака) |
| `aqi_http_active_connections` | Пик соединений (DDoS индикатор) |

Grafana-дашборд позволяет увидеть:
- Всплески HTTP 401/403/429 → возможная атака
- Рост активных соединений → возможный DDoS
- Аномально долгие запросы → попытка timing-атаки

### 14.3 Request ID трассировка

Каждый запрос получает уникальный `X-Request-Id`. Этот ID:
- Присваивается Nginx на входе
- Пробрасывается в Go через `chimiddleware.RequestID`
- Возвращается клиенту в заголовке ответа
- Присутствует во всех log-записях этого запроса

Позволяет отследить полный путь любого запроса через все компоненты.

## 16. СБРОС ПАРОЛЯ

### 16.1 Схема безопасного сброса

```
1. Пользователь: POST /auth/forgot-password {email: "..."}
2. Сервер: генерирует token = crypto/rand (32 байта) → hex
3. Сервер: сохраняет в Redis: "password_reset:<token>" → email, TTL=1ч
4. Сервер: отправляет email со ссылкой: /reset-password?token=<token>
5. Сервер: возвращает HTTP 200 (ВСЕГДА, даже если email не существует)

6. Пользователь переходит по ссылке из письма
7. POST /auth/reset-password {token: "...", new_password: "..."}
8. Сервер: Redis.GetDel("password_reset:<token>") → email (удаляет токен)
9. Сервер: хеширует новый пароль Argon2id
10. Сервер: обновляет пароль в БД
```

**Свойства безопасности:**
- Токен одноразовый (`GetDel` — атомарно читает и удаляет)
- TTL 1 час — истёкшие токены удаляются автоматически
- Ответ всегда `200 OK` — нельзя узнать существует ли email в системе
- Токен случайный (256 бит) — перебор невозможен

## 17. ПУБЛИЧНЫЙ ВИДЖЕТ

### 17.1 Особенности безопасности виджета

Виджет — публичный эндпоинт без аутентификации. Он отдаёт только агрегированные данные:

```
Доступно без токена:
  GET /widget/              — HTML страница виджета
  GET /widget/data          — текущий AQI по точкам
  GET /widget/forecast      — прогноз
  GET /widget/weather       — погода

Недоступно без токена:
  GET /api/v1/measurements  — сырые измерения
  GET /api/v1/users         — данные пользователей
  POST /api/v1/sensors      — создание датчиков
```

### 17.2 Rate limiting для виджета

Виджет имеет отдельный более мягкий лимит (300 req/мин), так как может встраиваться на сайты с большим трафиком.

### 17.3 Защита от злоупотребления виджетом

- Агрегированные данные (нет персональных данных)
- Rate limiting предотвращает нагрузочные атаки
- CORS не ограничивает origin — виджет намеренно публичен
- Нет ввода данных — только GET-запросы на чтение
